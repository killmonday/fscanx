# 计划：BL-MEM-001 + BL-MEM-002 内存优化

日期：2026-09-23
状态：已完成

## 目标

1. 修复 ReadRawWithSize 池污染数据竞争（P0 正确性）
2. POC 响应读取限长 4MB + redis 16KB（P1 内存优化）

## 用户决策记录

- 指纹读取上限保持 192KB 不变（放弃 BufPool 降档，避免检测语义变化）
- POC body 上限 4MB，超限静默截断
- 两项都执行

## 执行步骤

1. BL-MEM-001：
   - webScanTask.go ReadRawWithSize：所有 return 路径改为拷贝后返回（`append([]byte(nil), ...)`），加注释说明池污染原因
   - webScanTask.go DoWebScan：删除共享 client.Timeout 赋值行（冗余 + 数据竞争）
   - 新增 Plugins/webScanTask_test.go：并发隔离测试（-race 下验证）+ 错误路径测试
2. BL-MEM-002：
   - eval.go getRespBody：raw 与 gzip 解压后各加 `io.LimitReader(4MB)`，常量 maxPocBodyBytes，注释截断语义
   - redis.go readreply：`io.LimitReader(conn, 16KB)`，注释截断语义
   - go.mod：移除 pond 行 `// indirect` 误标（手动，不跑 tidy）
   - 新增 PocScan/lib/eval_test.go：10MB body 限长测试 + gzip 解压炸弹测试
   - 新增 Plugins/redis_test.go：net.Pipe 超限测试
3. 验证：go build ./... / go vet ./... / go test -race ./Plugins/ ./PocScan/lib/
4. reviewer 验证（sonnet 级，<5 文件）+ deslop + 回归
5. 文档同步：CHANGELOG、backlog 状态、项目控制台、模块文档

## 风险

- getRespBody 限长可能影响依赖超大响应的 POC 判定（已与用户确认 4MB + 静默截断）
- 并发测试在 CI 慢机器上可能偶发时序问题（用足够迭代 + race 探测器兜底）

## 验证方式

见两个 backlog item 的验收条件。

## 决策记录

- pond"常驻协程"优化项删除：critic 评审指出 pond v1.9.2 `New` 第一参数是 maxWorkers（已读模块缓存源码证实），worker 按需创建、空闲 5s 回收，初稿分析前提错误。
- go.mod 用手动改注释替代 go mod tidy：避免 tidy 带来的无关依赖变更（最小必要修改原则）。

## 结果

- BL-MEM-001 完成：ReadRawWithSize 全部返回路径拷贝、defer 改为先 Reset 后 Put（初版只修了返回别名，-race 测试抓出了 Reset 与池取用者的竞争，属计划外必要修正）、删除共享 client.Timeout 赋值。
- BL-MEM-002 完成：getRespBody maxPocBodyBytes=4MB 双路径限长、readreply 16KB、go.mod pond 误标移除。
- 新增测试 5 个：并发池隔离、错误路径拷贝语义、readreply 上限、getRespBody 原始限长、gzip 解压防护。
- 计划外修复：ms17010_test.go nil conn panic、qqwry_test.go 资源缺失 panic（两者阻塞整包测试，不修则验收条件字面不可达成）。
- 验证证据：`go test -race ./Plugins/ ./PocScan/lib/` ok（18.4s）、`go vet ./Plugins/ ./PocScan/lib/` ok、`go build .` ok；reviewer（sonnet）APPROVE；deslop 通过（仅注释收紧）；post-deslop 回归 ok。
- 风险跟进：redis >16KB 回复残余字节复用风险、mylib 14 个包 vet 债务，均记录于 docs/modules/02-资源与内存控制模块.md 后续开发事项。
