## BL-MEM-001 修复 ReadRawWithSize 池污染数据竞争

- 模块：资源与内存控制
- 优先级：P0（正确性 bug：静默产出错误扫描结果，默认 `-tn 60` 即可触发，用户无从察觉）
- 状态：已完成
- 当前阶段：持续迭代
- 价值：消除并发下指纹/标题识别结果互相覆盖的数据竞争，保证扫描结果可信。
- 关联模块文档：docs/modules/02-资源与内存控制模块.md
- 关联计划：plans/2026-09-23-BL-MEM-001-BL-MEM-002-内存优化.md
- 关联代码：Plugins/webScanTask.go
- 验收状态：待验收

### 背景

`ReadRawWithSize`（Plugins/webScanTask.go:681）存在池污染问题：

1. `raw := BufBuildPool.Get()` 后 `return raw.Bytes()`——返回切片与池化 buffer 底层数组共享，但 buffer 已被 `Put` 回池。任务 A 返回的 body 会被任务 B 的写入覆盖。
2. defer LIFO 顺序：先注册 `defer raw.Reset()`（685 行）、后注册 `defer BufBuildPool.Put(raw)`（686 行），返回时**先执行 Put 后执行 Reset**——A 的 Reset 会清掉 B（已从池中拿到该 buffer）正在写的数据。
3. 错误路径同样受影响：webScanTask.go:725 `return raw.Bytes(), err` 也返回池化内存；调用方 DoWebScan（443-445 行）忽略 err 后仍继续使用 body。

同属正确性的附带修复：`DoWebScan`（webScanTask.go:422）每次请求对共享 `lib.Client`/`lib.ClientNoRedirect` 赋值 `client.Timeout`，与 InitHttpClient（client.go:82-88）的初始化重复，且是并发数据竞争，删除该行。

### 范围

- ReadRawWithSize 所有返回路径（正常 + 错误）拷贝数据后返回，池化 buffer 内存不逸出池外
- 删除 DoWebScan 中对共享 client.Timeout 的赋值行
- 新增并发单测覆盖正常路径与错误路径

### 不做

- 不改 BufPool/BufBuildPool 的池大小与结构（属 BL-MEM-002）
- 不改指纹读取上限（属 BL-MEM-002）
- 不删除 webScanTask.go:739-769 注释死代码（记入 docs/后续开发事项.md）

### 验收条件

- [ ] 新增单测：`go test -race ./Plugins/` 下，多 goroutine 并发调用 ReadRawWithSize 读取不同 httptest 响应，各自返回内容与源数据逐字节一致（证明无池污染）
- [ ] 同一单测覆盖错误路径（响应体读取中途超时/中断场景），调用方拿到的已读部分不与池共享
- [ ] DoWebScan 不再对 lib.Client/lib.ClientNoRedirect.Timeout 赋值（grep 确认无 `client.Timeout =` 残留于 Plugins/）

## BL-MEM-002 响应体读取限长与缓冲区降档

- 模块：资源与内存控制
- 优先级：P1
- 状态：已完成
- 当前阶段：持续迭代
- 价值：消除 webpoc 模式内存瞬时峰值的主因：POC 路径不再全量读大响应（单请求读入上限 4MB，gzip 路径瞬时约 8MB，PocNum=30 并发最坏约 240MB 且有硬上界）；堵住 gzip 解压炸弹；redis 探测不再时间有界字节无界。
- 关联模块文档：docs/modules/02-资源与内存控制模块.md
- 关联计划：plans/2026-09-23-BL-MEM-001-BL-MEM-002-内存优化.md
- 关联代码：PocScan/lib/eval.go、Plugins/webScanTask.go、Plugins/redis.go、common/flag.go
- 验收状态：待验收

### 背景

外部内存优化方案核对结论：方案中的"关 keep-alive、全局 client、worker 池、sync.Pool、pond 协程池"本项目已实现或已符合目标状态（critic 评审 + pond v1.9.2 源码核实：`New` 第一参数是 maxWorkers，worker 按需创建、空闲 5s 回收，无预创建常驻协程——初稿中"pond 常驻协程过多"一条系分析错误，删除）。真实遗留问题：

1. **POC 路径无上限读 body**：`getRespBody`（PocScan/lib/eval.go:685）对响应体 `io.ReadAll` 无上限；gzip 解压后再 `io.ReadAll` 也无上限（解压炸弹无防护）。webpoc 模式下 PocNum（默认 30）个 worker 同时全量读大响应，是内存瞬时峰值的主要来源。`ParseResponse`（eval.go:680）丢弃 getRespBody 的 err，因此超限行为定为**静默截断**（与现状错误处理语义一致），在代码注释与模块文档中记录该语义。
2. **web 指纹路径 BufPool 192KB/任务**：经用户决策**保持 192KB 不变**（避免检测语义变化），本轮不动。
3. **redis readreply 时间有界、字节无界**：`io.ReadAll(conn)`（Plugins/redis.go:310）上一行已有 1 秒 SetReadDeadline，但千兆内网 1 秒可拉入上百 MB。加 16KB LimitReader；现有 `if len(bytes) > 0 { err = nil }`（311-313 行）会把超限截断伪装成成功，加注释说明截断语义。

### 范围

- getRespBody：原始 body 与 gzip 解压后内容分别加 LimitReader，上限 4MB（用户已确认），超限静默截断并注释
- redis readreply 加 16KB LimitReader 并注释截断语义
- go.mod 中移除 pond 行的误标 `// indirect` 注释（该包被 common/flag.go 直接 import；手动改注释，不跑 go mod tidy 以避免无关依赖变动）
- 为限长行为补单测（锚定具体上限值）

### 不做

- 不改 pond 参数（已核实当前即目标状态）
- 不下调 BufPool 192KB / 指纹读取上限（用户决策：保持检测语义不变）
- 不改 CEL env 每次 executePoc 重建的设计（记入 docs/后续开发事项.md）
- 不动 qqwry.dat 27MB 全量加载（IP 归属地二分查找需随机访问，功能必需静态内存）
- 不删除 simplehttp 死代码与 webScanTask.go 注释死代码（记入 docs/后续开发事项.md）
- 不引入 GOGC/GOMEMLIMIT 调整与 pprof 端口（记入模块文档运行建议）
